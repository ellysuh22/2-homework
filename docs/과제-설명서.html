0. 이 과제로 만든 것 — 30초 요약

먼저 “무엇을 만들었는가”를 한 문장과 한 그림으로 잡고 갑시다.

한 문장 요약 터미널(검은 화면)에서 실행되는 4지선다 퀴즈 게임을 파이썬으로 만들고, 퀴즈와 점수를 state.json 파일에 저장해서 프로그램을 껐다 켜도 유지되게 했으며, 만드는 과정 전체를 Git으로 기록해 GitHub에 공개했습니다.

제출물이 왜 이렇게 3개인가

제출물무엇인가왜 필요한가
main.py파이썬 코드 파일 하나. 프로그램의 몸통.“동작하는 프로그램”을 만들었다는 증거
state.json퀴즈·점수를 적어두는 데이터 저장 파일“껐다 켜도 유지된다(데이터 영속성)”는 증거
GitHub 저장소만들어온 과정이 전부 기록된 온라인 창고“혼자 한 번에 만든 게 아니라 단계별로 만들었다”는 증거

1. 파이썬 기초 용어

과제 목표에 “변수, 자료형, 조건문, 반복문, 함수를 설명할 수 있어야 한다”가 적혀 있습니다. 하나씩 갑니다.

변수 (variable) 이름표가 붙은 상자
뜻
값을 담아두고 이름으로 다시 꺼내 쓰는 것입니다.
비유
택배 상자에 “겨울옷”이라고 매직으로 써 붙이는 것과 같습니다. 나중에 상자를 다 열어보지 않아도 “겨울옷” 상자만 찾으면 됩니다.
왜 쓰나
같은 값을 여러 곳에서 쓸 때 한 곳만 고치면 전부 바뀌기 때문입니다. 힌트 감점을 5점→3점으로 바꾸고 싶으면 HINT_PENALTY = 5 한 줄만 고치면 됩니다.
내 코드에서
correct = 0 (맞힌 개수), total (푼 문제 수), HINT_PENALTY = 5 (힌트 감점), STATE_FILE (저장 파일 경로)
💬 이렇게 말하기
“변수는 값에 이름을 붙여 저장해 두는 공간입니다. 저는 감점 점수를 HINT_PENALTY라는 변수로 맨 위에 빼두어서, 규칙이 바뀌면 그 한 줄만 고치면 되도록 만들었습니다.”

자료형 5가지 — int, str, bool, list, dict

자료형은 “이 값이 어떤 종류인가”입니다. 숫자인지, 글자인지, 참/거짓인지에 따라 컴퓨터가 할 수 있는 일이 달라집니다.

💬 자료형 질문이 나오면 이렇게 “int는 계산할 수 있는 숫자, str은 글자, bool은 참/거짓 두 가지뿐인 값입니다. list는 순서가 있어서 몇 번째로 꺼내고, dict는 이름표(키)를 붙여서 이름으로 꺼냅니다. 제 프로그램에서 선택지 4개는 순서가 중요하니까 list로, 게임 기록은 날짜·점수처럼 항목마다 이름이 필요하니까 dict로 저장했습니다.”
조건문 if / elif / else 갈림길
뜻
“만약 ~라면 이것, 아니면 저것”을 시키는 문법입니다.
비유
자판기입니다. 1번을 누르면 콜라, 2번을 누르면 사이다, 그 외 번호면 “없는 번호입니다” 안내가 나옵니다.
내 코드에서
메뉴 처리 부분이 그대로 자판기입니다. if choice == 1 → 퀴즈 풀기, elif choice == 2 → 퀴즈 추가 … else → 종료.
💬 이렇게 말하기
“if는 조건이 맞을 때, elif는 그게 아니고 다른 조건일 때, else는 나머지 전부일 때 실행됩니다. 메뉴 1~6번을 이 구조로 나눠서 각 기능에 연결했습니다.”
반복문 for / while 같은 일 여러 번
for의 뜻
횟수가 정해진 반복. “이 목록에 있는 것 전부 하나씩”
while의 뜻
횟수를 모르는 반복. “조건이 만족될 때까지 계속”
비유
for는 “장바구니에 담긴 물건 5개를 하나씩 계산대에 올린다”(개수를 안다).
while은 “손님이 다 나갈 때까지 문을 연다”(몇 명 올지 모른다).
내 코드에서
for — 뽑은 문제를 하나씩 출제: for number, quiz in enumerate(selected_quizzes, start=1)
while — 올바른 숫자가 들어올 때까지 계속 다시 물음: while True: in input_int()
💬 이렇게 말하기
“몇 번 돌지 아는 경우는 for, 모르는 경우는 while을 씁니다. 문제 5개를 출제하는 건 개수를 아니까 for, 사용자가 언제 제대로 입력할지는 모르니까 입력 검증은 while로 만들었습니다.”
함수 (function) 기능 하나를 묶은 도구
뜻
자주 쓰는 작업에 이름을 붙여 묶어둔 것. 이름만 부르면 그 작업이 실행됩니다.
비유
전자레인지 “해동” 버튼입니다. 안에서 무슨 일이 벌어지는지 몰라도 버튼만 누르면 됩니다. 누를 때마다 매번 시간·출력을 다시 설정할 필요가 없습니다.
매개변수
함수에 넣어주는 값. 전자레인지에 넣는 “음식”에 해당. input_int("선택: ", 1, 6)에서 1과 6이 매개변수(허용 범위)입니다.
반환값
함수가 돌려주는 결과. 데워져 나온 음식. input_int()는 검증을 통과한 숫자를 돌려줍니다.
내 코드에서
숫자 입력 검증이 메뉴·정답·문제 수·삭제 번호 등 5군데에서 필요했는데, input_int() 함수 하나로 묶어서 모든 곳에서 재사용했습니다.
💬 이렇게 말하기
“함수는 반복되는 작업에 이름을 붙여 재사용하는 도구입니다. 저는 숫자 입력 검증을 input_int() 하나로 만들어서, 같은 검증 코드를 5번 복사하지 않고 다섯 곳에서 불러 쓰도록 했습니다. 검증 규칙이 바뀌어도 한 곳만 고치면 됩니다.”

2. 클래스와 객체 — 붕어빵 틀 이야기

이 과제에서 가장 중요한 개념이자, 평가자가 가장 많이 물어볼 부분입니다.

클래스 (class) 설계도 / 붕어빵 틀
뜻
같은 모양의 데이터를 여러 개 만들기 위한 틀입니다. “퀴즈라는 건 문제·선택지·정답·힌트를 가진다”는 규칙을 먼저 정의합니다.
왜 쓰나
클래스가 없으면 퀴즈 6개를 만들 때 변수 24개(문제6+선택지6+정답6+힌트6)를 따로 관리해야 합니다. 클래스를 쓰면 퀴즈 하나가 덩어리 하나로 다뤄집니다.
내 프로젝트
Quiz(문제 한 개 담당)와 QuizGame(게임 전체 담당) 두 개를 만들었습니다. 과제 요구인 “최소 2개 클래스”를 충족합니다.
💬 이렇게 말하기
“클래스는 붕어빵 틀이고 객체는 그 틀로 구워낸 붕어빵입니다. 저는 문제 하나를 담당하는 Quiz와 게임 전체를 담당하는 QuizGame으로 역할을 나눴습니다. 이렇게 나누면 문제 형식을 바꿀 때는 Quiz만, 메뉴 흐름을 바꿀 때는 QuizGame만 손대면 됩니다.”
객체 (object) / 인스턴스 틀로 찍어낸 실물
뜻
클래스로 실제로 만들어낸 하나하나입니다. 틀은 1개지만 붕어빵은 6개일 수 있습니다.
내 코드에서
Quiz("파이썬에서 리스트를 만들 때…", ["( )","[ ]","{ }","< >"], 2, "순서가 있고…") — 이렇게 부르는 순간 퀴즈 객체 1개가 만들어집니다. 기본 퀴즈 5개가 이렇게 생성됩니다.
💬 이렇게 말하기
“클래스 이름을 함수처럼 부르면 객체가 만들어집니다. 제 프로그램은 시작할 때 기본 퀴즈 5개를 Quiz 객체로 만들어서 리스트에 담아둡니다.”
__init__ (생성자) 태어날 때 딱 한 번
뜻
객체가 만들어지는 순간 자동으로 딱 한 번 실행되는 특별한 함수입니다. 처음 값을 채워 넣는 역할을 합니다.
비유
아기가 태어나면 출생신고서를 씁니다. 이름·생년월일·성별을 그때 한 번 기록하죠. __init__이 그 출생신고서입니다.
내 코드에서
def __init__(self, question, choices, answer, hint=""): — 퀴즈 객체가 태어날 때 문제·선택지·정답·힌트를 받아서 자기 안에 저장합니다.
💬 이렇게 말하기
“__init__은 생성자라고 부르는데, 객체가 만들어질 때 자동으로 실행돼서 초기값을 세팅합니다. 제가 Quiz(...)라고 쓰면 파이썬이 알아서 __init__을 호출해서 문제와 선택지를 채워 넣습니다.”
self “나 자신”
뜻
메서드 안에서 그 객체 자기 자신을 가리키는 단어입니다.
비유
붕어빵 6개가 나란히 있을 때 “내 팥소”라고 말하는 것과 같습니다. 3번 붕어빵이 “내 팥소”라고 하면 3번 것을 가리키고, 5번이 말하면 5번 것을 가리킵니다. 같은 코드인데 누가 말하느냐에 따라 대상이 달라집니다.
내 코드에서
self.question은 “이 퀴즈의 문제”입니다. 퀴즈 1번의 display()를 부르면 1번 문제가, 3번 것을 부르면 3번 문제가 출력됩니다. 코드는 딱 한 벌인데 말이죠.
💬 이렇게 말하기
“self는 ‘나 자신’이라는 뜻입니다. 퀴즈가 6개 있어도 출력 코드는 한 벌만 있으면 되는데, self.question이라고 쓰면 그 코드를 부른 퀴즈의 문제가 자동으로 들어가기 때문입니다.”
속성(attribute) vs 메서드(method) 가진 것 vs 하는 것
속성
객체가 가지고 있는 값. 명사입니다. → 퀴즈의 문제, 선택지, 정답, 힌트
메서드
객체가 할 수 있는 동작. 동사입니다. → 문제를 출력하다, 정답인지 확인하다
비유
스마트폰으로 치면 속성은 “색상, 저장용량, 배터리 잔량”이고 메서드는 “전화 걸기, 사진 찍기”입니다.
내 코드 (Quiz)
속성 4개: question choices answer hint
메서드 4개: display()(문제 출력) check()(정답 확인) to_dict()(저장용 변환) from_dict()(불러오기용 변환)
내 코드 (QuizGame)
속성 3개: quizzes(퀴즈 목록) best_score(최고 점수) history(게임 기록)
메서드: show_menu() run() play_quiz() add_quiz() list_quizzes() delete_quiz() show_score() load_state() save_state() input_int() 등
💬 이렇게 말하기
“속성은 그 객체가 가진 값, 메서드는 그 객체가 하는 일입니다. Quiz는 문제·선택지·정답을 가지고, 자기를 화면에 출력하고 채점하는 일을 합니다.”

3. 파일 저장과 JSON — 껐다 켜도 안 사라지는 이유

과제의 핵심 요구 중 하나인 “데이터 영속성”입니다.

먼저: 왜 파일에 저장해야 하나?

JSON 사람도 컴퓨터도 읽는 데이터 형식
읽는 법
“제이슨”이라고 읽습니다. JavaScript Object Notation의 줄임말입니다.
뜻
데이터를 { 이름: 값 } 형태로 적어두는 국제 표준 약속입니다. 파이썬의 dict와 모양이 거의 같아서 서로 변환이 쉽습니다.
비유
회원가입 종이 양식과 같습니다. “이름: 홍길동 / 나이: 20 / 취미: [독서, 등산]”처럼 항목 이름과 값을 짝지어 적습니다. 양식이 정해져 있으니 누가 읽어도 헷갈리지 않습니다.
왜 쓰나
① 사람이 파일을 열어 눈으로 읽을 수 있음 ② 파이썬에 json 기능이 기본 포함되어 별도 설치 불필요 ③ 어떤 프로그래밍 언어든 읽을 수 있는 표준
내 프로젝트
퀴즈 목록·최고 점수·게임 기록을 state.json에 저장합니다.
💬 이렇게 말하기
“JSON은 데이터를 이름과 값의 짝으로 적어두는 표준 형식입니다. 파이썬 딕셔너리와 구조가 같아서 변환이 간단하고, 파일을 그냥 열어봐도 사람이 읽을 수 있어서 저장 형식으로 골랐습니다.”

저장/불러오기가 실제로 어떻게 도는가

UTF-8 인코딩 한글이 깨지지 않게
뜻
글자를 컴퓨터가 저장할 숫자로 바꾸는 규칙(약속)입니다. UTF-8은 전 세계 문자를 다 담을 수 있는 표준입니다.
비유
모스 부호 약속표와 같습니다. 보내는 쪽과 받는 쪽이 같은 약속표를 써야 말이 통합니다. 다른 표를 쓰면 “ìë…•” 같은 깨진 글자가 나옵니다.
내 코드에서
open(STATE_FILE, "w", encoding="utf-8") — 읽을 때도 쓸 때도 utf-8로 통일했습니다.
json.dump(data, file, ensure_ascii=False) — 이 옵션을 꺼야 한글이 안 같은 코드가 아니라 “안녕” 그대로 저장됩니다.
💬 이렇게 말하기
“한글 문제를 저장해야 해서 인코딩을 UTF-8로 지정했습니다. 그리고 ensure_ascii=False 옵션을 줘서 파일을 열었을 때 한글이 그대로 보이도록 했습니다.”

실제 state.json 파일 내용

{
  "quizzes": [
    {
      "question": "파이썬에서 리스트를 만들 때 사용하는 괄호는?",
      "choices": ["( )", "[ ]", "{ }", "< >"],
      "answer": 2,
      "hint": "순서가 있고 나중에 값을 바꿀 수 있는 자료형에 쓰는 기호입니다."
    }
  ],
  "best_score": 80,
  "history": [
    { "date": "2026-08-04 20:04", "total": 5, "correct": 4, "score": 80 }
  ]
}

구조 읽는 법: 큰 이름표 3개(quizzes, best_score, history)가 있고, quizzes 안에 [ ]로 퀴즈들이 줄줄이 들어 있습니다. 퀴즈 하나마다 다시 { } 안에 문제·선택지·정답·힌트가 있습니다.

4. 예외 처리 — 프로그램이 안 죽게 만드는 법

과제에서 “잘못된 입력 처리”와 “try/except”를 명시적으로 요구합니다. 평가자가 직접 abc를 쳐볼 가능성이 높은 부분입니다.

try / except 일단 해보고, 실패하면 대처
뜻
try 블록의 코드를 일단 시도하고, 오류가 나면 프로그램이 죽는 대신 except 블록으로 넘어가서 수습합니다.
비유
우산을 들고 나가는 것과 같습니다. 비가 안 오면 그냥 가고(try 성공), 비가 오면 우산을 펴서 대처합니다(except). 우산이 없으면 그냥 홀딱 젖습니다(프로그램 강제 종료).
내 코드 ①
숫자 변환: int("abc")는 오류가 납니다. 이걸 try로 감싸고 except ValueError에서 “⚠️ 숫자가 아닙니다”를 출력한 뒤 다시 물어봅니다.
내 코드 ②
파일 읽기: except (OSError, json.JSONDecodeError, KeyError, TypeError) — 파일이 깨졌거나, 형식이 이상하거나, 필요한 항목이 없어도 프로그램이 죽지 않고 기본 퀴즈로 복구합니다.
💬 이렇게 말하기
“try/except는 오류가 날 수 있는 코드를 감싸서, 실제로 오류가 나도 프로그램이 강제 종료되지 않게 하는 장치입니다. 저는 숫자 변환 실패와 저장 파일 손상 두 곳에 적용했습니다.”
평가자가 입력해볼 것어떤 종류의 오류인가내 프로그램의 반응
1 (앞뒤 공백)공백 포함 입력.strip()으로 공백을 지우고 정상 처리 ✅
abc숫자 변환 실패 (ValueError)“⚠️ 숫자가 아닙니다” → 다시 입력받음
9 (메뉴에서)허용 범위 초과“⚠️ 잘못된 입력입니다. 1-6 사이의 숫자를 입력하세요” → 다시
그냥 Enter빈 입력“⚠️ 입력이 비어 있습니다” → 다시 입력받음
Ctrl + CKeyboardInterrupt“⚠️ 입력이 중단되었습니다. 저장 후 안전하게 종료합니다” → 저장하고 정상 종료
state.json을 일부러 망가뜨림JSONDecodeError“⚠️ 저장 파일이 손상되어 기본 퀴즈로 복구합니다” → 기본 5문제로 실행
state.json 파일을 지움파일 없음“📂 저장된 데이터가 없어 기본 퀴즈로 시작합니다” → 정상 실행
⚠️ 여기가 감점 포인트입니다 대부분의 과제가 “정상 동작”은 하는데 이상한 입력에서 빨간 오류 메시지를 내며 죽습니다. 평가자는 거의 항상 abc나 Ctrl+C를 눌러봅니다. 제 프로그램은 위 7가지 경우를 전부 처리했고, Ctrl+C를 눌러도 데이터를 저장한 뒤 종료한다는 점을 꼭 말씀하세요.

5. Git 용어 총정리

과제에서 init · add · commit · push · pull · checkout · clone 7개를 각각 한 번 이상 쓰라고 요구합니다. 여기가 가장 설명하기 어려운 부분이라 그림부터 봅니다.

Git이란? 작업 기록 + 되돌리기
뜻
파일이 언제, 누가, 무엇을, 왜 바꿨는지 전부 기록해두고 언제든 그 시점으로 되돌아갈 수 있게 해주는 도구입니다.
비유
게임의 세이브 파일입니다. 보스 앞에서 세이브해두면, 죽어도 그 지점부터 다시 시작할 수 있습니다. Git 없이 작업하는 건 세이브 없이 게임하는 것과 같습니다.
Git 없으면?
과제_최종.py, 과제_최종_진짜최종.py, 과제_최종_진짜진짜최종_수정본.py… 이렇게 됩니다. 어느 게 최신인지 아무도 모릅니다.
GitHub와 차이
Git은 내 컴퓨터에서 도는 프로그램, GitHub는 그 기록을 올려두는 인터넷 창고(웹사이트)입니다. 카카오톡(앱)과 카카오 서버의 관계와 비슷합니다.
💬 이렇게 말하기
“Git은 코드의 변경 이력을 저장하고 되돌릴 수 있게 해주는 버전 관리 도구입니다. GitHub는 그 기록을 인터넷에 올려 백업하고 공유하는 서비스고요. 저는 기능 하나를 완성할 때마다 커밋해서 총 17개의 기록을 남겼습니다.”

⭐ 가장 중요한 그림 — Git의 4개 공간

Git 명령어가 헷갈리는 이유는 파일이 머무는 공간이 4개인데 그걸 모르고 명령어만 외우기 때문입니다. 이 그림 하나면 7개 명령어가 전부 이해됩니다.

명령어 7개 하나씩

git init 1️⃣ 시작
뜻
이 폴더에서 Git 기록을 시작하겠다고 선언합니다. 딱 한 번만 합니다.
비유
새 공책 첫 장에 “2026 업무일지”라고 제목을 쓰는 것. 이제부터 여기에 기록이 쌓입니다.
일어나는 일
폴더 안에 .git이라는 숨김 폴더가 생깁니다. 여기에 모든 기록이 저장됩니다. 이 폴더를 지우면 이력이 전부 날아갑니다.
💬 한마디
“프로젝트 폴더에서 git init을 실행해 버전 관리를 시작했습니다.”
git add 2️⃣ 담기
뜻
바뀐 파일 중 이번 기록에 포함할 것만 골라서 대기 장소(스테이징)에 올립니다.
비유
마트에서 장바구니에 담는 것입니다. 아직 계산(commit)은 안 했습니다. 담았다가 뺄 수도 있습니다.
왜 이 단계가 있나
파일 10개를 고쳤어도 “메뉴 기능”과 관련된 3개만 먼저 기록하고 싶을 수 있기 때문입니다. 기록을 의미 단위로 깔끔하게 나누기 위한 장치입니다.
💬 한마디
“git add는 커밋할 파일을 골라 담는 단계입니다. 장바구니에 담는 것에 비유할 수 있고, 이 단계가 있어서 변경사항을 기능별로 나눠 커밋할 수 있습니다.”
git commit 3️⃣ 확정 저장
뜻
장바구니에 담은 내용을 “이런 작업을 했다”는 설명(메시지)과 함께 확정 저장합니다. 이 하나하나가 되돌아갈 수 있는 세이브 포인트입니다.
비유
계산대에서 영수증을 받는 것. 영수증에는 날짜와 품목이 찍힙니다. 나중에 “언제 뭘 샀지?”를 영수증으로 확인합니다.
좋은 메시지
❌ 수정, ㅇㅇ, update — 나중에 아무 도움이 안 됨
✅ Feat: 퀴즈 출제 기능 구현 — 뭘 했는지 바로 보임
접두어 규칙
Feat 새 기능 / Fix 오류 수정 / Docs 문서 작업 / Refactor 동작은 그대로 두고 코드 정리 / Chore 설정·잡일
내 프로젝트
총 17개 커밋 (요구: 10개 이상 ✅). 전부 이 접두어 규칙을 지켰습니다.
💬 한마디
“커밋은 변경사항을 설명과 함께 확정 저장하는 것입니다. 저는 기능 하나를 완성할 때마다 커밋해서, 나중에 어느 시점에 무슨 기능이 들어갔는지 이력만 봐도 알 수 있게 만들었습니다.”
git push 4️⃣ 올리기
뜻
내 컴퓨터에 쌓인 커밋들을 GitHub(인터넷)로 올립니다.
비유
휴대폰 사진을 클라우드에 백업하는 것. 폰이 고장 나도 사진은 남습니다.
중요
commit만 하고 push를 안 하면 GitHub에는 아무것도 없습니다. 제출은 GitHub 주소로 하므로, 마지막에 push했는지 반드시 확인해야 합니다.
💬 한마디
“push는 내 컴퓨터의 커밋 기록을 GitHub에 올리는 명령입니다. 커밋은 내 컴퓨터에만 남기 때문에, 백업하고 제출하려면 push가 반드시 필요합니다.”
git clone 5️⃣ 통째로 내려받기
뜻
GitHub에 있는 저장소를 내 컴퓨터로 통째로 복사해 옵니다. 코드뿐 아니라 과거 이력 전부를 함께 가져옵니다.
비유
도서관 책을 통째로 복사해서 집으로 가져오는 것. 처음 한 번만 합니다.
언제 쓰나
새 컴퓨터에서 작업을 이어받을 때, 남의 프로젝트를 받아볼 때, 팀에 새로 합류할 때.
내 실습
과제 요구사항대로, 완성된 저장소를 별도 폴더에 clone한 뒤 → README를 한 줄 고쳐 commit·push → 원래 폴더에서 pull로 받아왔습니다.
💬 한마디
“clone은 GitHub 저장소를 이력까지 통째로 내 컴퓨터에 복제하는 명령입니다. 저는 실습으로 제 저장소를 다른 폴더에 clone해서 두 곳에서 작업하는 상황을 만들어봤습니다.”
git pull 6️⃣ 최신으로 갱신
뜻
GitHub에 새로 올라온 변경사항만 내 컴퓨터로 받아와 합칩니다.
clone과 차이
clone은 처음 한 번 통째로 받는 것(집에 없던 책을 가져옴), pull은 이미 있는 것을 최신으로 업데이트하는 것(앱 업데이트).
비유
단톡방에 안 들어와 있는 동안 쌓인 새 메시지만 받아오는 것.
내 실습
clone한 폴더에서 README를 수정해 push한 뒤, 원래 작업 폴더에서 git pull로 그 변경을 가져와 반영을 확인했습니다.
💬 한마디
“pull은 GitHub의 최신 변경사항을 내 컴퓨터로 받아오는 명령입니다. clone은 처음 한 번 전체를 받는 것이고, pull은 이후에 바뀐 부분을 갱신하는 것이라는 점이 다릅니다.”
git checkout 7️⃣ 작업 공간 이동
뜻
브랜치를 옮겨 다니거나, 과거 특정 시점으로 돌아갑니다. -b 옵션을 붙이면 새 브랜치를 만들면서 바로 이동합니다.
비유
TV 채널을 바꾸는 것. 채널을 바꾸면 화면 내용이 통째로 바뀌지만, 원래 채널이 사라진 건 아닙니다.
내 프로젝트
git checkout -b feature/play-quiz — 퀴즈 풀기 기능을 만들 별도 브랜치를 만들어 이동했습니다.
💬 한마디
“checkout은 브랜치를 이동하는 명령입니다. 저는 퀴즈 풀기 기능을 만들 때 feature/play-quiz라는 브랜치를 새로 만들어서 그쪽으로 이동해 작업했습니다.”

브랜치와 병합 — 왜 나눠서 작업했나

브랜치 (branch) 평행세계 / 안전한 실험실
뜻
본 작업(main)은 그대로 둔 채, 따로 갈라져 나와 작업하는 복사된 흐름입니다.
비유
문서를 “다른 이름으로 저장”해서 마음껏 실험해보는 것과 같습니다. 망쳐도 원본은 멀쩡합니다. 잘되면 원본에 반영하고, 안 되면 그냥 버리면 됩니다.
왜 필요한가
혼자 할 때도 “새 기능을 만들다가 기존에 잘 되던 것까지 망가지는” 사고를 막아줍니다. 팀에서는 여러 명이 서로 방해하지 않고 동시에 작업할 수 있게 해줍니다.
병합(merge)
따로 만든 브랜치의 작업을 다시 main으로 합치는 것입니다. 실험이 성공했으니 원본에 반영하는 단계입니다.
💬 한마디
“브랜치는 원본을 건드리지 않고 따로 작업하는 공간입니다. 퀴즈 풀기 기능이 이 프로그램에서 가장 복잡한 부분이라, feature/play-quiz 브랜치를 따로 만들어 작업하고, 정상 동작을 확인한 뒤 main에 병합했습니다.”
.gitignore 기록하지 말 것 목록
뜻
Git이 추적하지 않을 파일 목록을 적어두는 파일입니다.
비유
사진 백업할 때 “스크린샷 폴더는 빼고”라고 설정하는 것과 같습니다. 굳이 백업할 필요 없는 것들을 제외합니다.
내 프로젝트
__pycache__/(파이썬이 자동 생성하는 임시 파일), .DS_Store(맥이 만드는 숨김 파일), state.json(실행하면 자동 생성되는 개인 데이터)
state.json을 뺀 이유
이건 사람마다 다른 개인 플레이 기록입니다. 코드가 아니라 실행 결과물이라 저장소에 올릴 이유가 없고, 없어도 프로그램이 기본 퀴즈로 알아서 시작하도록 만들었습니다.
💬 한마디
“.gitignore는 버전 관리에서 제외할 파일을 지정합니다. 임시 파일과 개인 실행 기록인 state.json을 제외해서, 저장소에는 코드와 문서만 남도록 했습니다.”

보너스 기능 5개 (선택 과제인데 전부 구현함)

보너스어떻게 구현했나설명 포인트
랜덤 출제random.sample(self.quizzes, total)목록에서 겹치지 않게 뽑아서 순서도 섞습니다. 같은 문제가 두 번 나오지 않습니다.
문제 수 선택시작 전 “몇 문제를 푸시겠습니까?”1~등록된 개수 사이만 허용하도록 검증합니다.
힌트정답 입력창에서 5를 누르면 표시힌트를 1회 볼 때마다 5점 차감. 점수가 음수가 되지 않게 max(0, …)로 막았습니다.
퀴즈 삭제메뉴 4번, list.pop() 후 저장삭제 후 곧바로 파일에 반영합니다.
점수 히스토리매 게임마다 날짜·문제수·정답수·점수 기록최고 점수뿐 아니라 전체 기록을 남기고, 최근 5회를 보여줍니다.

점수 계산식 설명

score = max(0, round(correct / total * 100) - hint_count * 5)

풀어서 읽으면: “맞힌 개수 ÷ 푼 개수 × 100”으로 100점 만점 환산하고(round는 반올림), 힌트를 본 횟수만큼 5점씩 뺀 뒤, max(0, …)로 아무리 빼도 0점 아래로는 안 내려가게 막았습니다. 예: 5문제 중 4개 정답에 힌트 1회 → 80 − 5 = 75점.

7. 평가자 예상 질문 20개 + 답변 대본

그대로 읽어도 되도록 답변을 문장으로 써두었습니다. 소리 내어 한 번씩 읽어보세요.

Q1. 이 프로그램이 뭐 하는 건지 30초로 설명해주세요.
터미널에서 실행하는 4지선다 퀴즈 게임입니다. 메뉴에서 번호를 고르면 퀴즈 풀기, 추가, 목록, 삭제, 점수 확인을 할 수 있습니다. 파이썬 기초 문법을 주제로 기본 문제 5개를 넣어뒀고, 사용자가 문제를 더 추가할 수 있습니다. 추가한 문제와 최고 점수는 state.json 파일에 저장돼서 프로그램을 껐다 켜도 그대로 유지됩니다.
Q2. 왜 퀴즈 주제를 “파이썬 기초 문법”으로 골랐나요?
이번 과제에서 제가 직접 쓴 개념들 — 리스트, 불린, __init__, 딕셔너리, 반복문 — 을 그대로 문제로 만들었습니다. 프로그램을 만들면서 쓴 문법이 곧 문제가 되니까, 완성하는 과정 자체가 복습이 되도록 주제를 골랐습니다.
Q3. 클래스를 왜 2개로 나눴나요? 하나면 안 되나요?
가능은 하지만 관리가 어려워집니다. Quiz는 문제 한 개가 가진 정보와 그 문제 하나에 대한 동작만 담당하고, QuizGame은 메뉴 흐름·채점·저장 같은 게임 전체를 담당합니다. 이렇게 나누면 문제 형식을 바꿀 때는 Quiz만, 메뉴를 바꿀 때는 QuizGame만 고치면 되기 때문에 어디를 고쳐야 할지 명확하고 서로 영향을 주지 않습니다.
Q4. __init__과 self가 뭔가요?
__init__은 생성자입니다. 객체가 만들어지는 순간 자동으로 한 번 실행돼서 초기값을 채워 넣습니다. 아기가 태어날 때 출생신고서를 쓰는 것과 같습니다.
self는 “나 자신”이라는 뜻으로, 그 메서드를 부른 객체 자기 자신을 가리킵니다. 퀴즈가 6개 있어도 출력 코드는 한 벌만 있으면 되는데, self.question이라고 쓰면 부른 쪽 퀴즈의 문제가 자동으로 들어가기 때문입니다.
Q5. list와 dict의 차이를 설명해보세요.
둘 다 여러 값을 담지만 꺼내는 방법이 다릅니다. list는 순서가 있어서 “몇 번째 것”으로 꺼내고, dict는 이름표(키)를 붙여서 “무슨 이름의 것”으로 꺼냅니다. 제 프로그램에서 선택지 4개는 1·2·3·4번 순서가 중요해서 list로 만들었고, 게임 기록은 날짜·문제수·점수처럼 항목마다 이름이 필요해서 dict로 저장했습니다.
Q6. for와 while은 언제 각각 쓰나요?
반복 횟수를 아는 경우는 for, 모르는 경우는 while을 씁니다. 문제 5개를 하나씩 출제하는 건 개수를 아니까 for를 썼고, 사용자가 올바른 숫자를 언제 입력할지는 모르니까 입력 검증은 while로 “맞을 때까지” 반복하게 만들었습니다.
Q7. 왜 JSON으로 저장했나요? 그냥 텍스트 파일은 안 되나요?
가능하지만 불편합니다. 그냥 텍스트로 저장하면 나중에 읽을 때 어디까지가 문제고 어디부터가 선택지인지 직접 잘라내는 코드를 짜야 합니다. JSON은 이름과 값을 짝지어 적는 표준 형식이라 파이썬이 json.load() 한 줄로 알아서 읽어줍니다. 파이썬 딕셔너리와 구조가 같아서 변환도 쉽고, 파일을 열어보면 사람도 읽을 수 있습니다.
Q8. 저장은 정확히 언제 되나요?
데이터가 바뀌는 순간마다 바로 저장합니다. 퀴즈를 추가했을 때, 삭제했을 때, 게임을 한 판 끝냈을 때입니다. 그리고 Ctrl+C로 중단해도 종료 직전에 한 번 더 저장합니다. 종료할 때만 저장하면 갑자기 꺼졌을 때 다 날아가기 때문에, 바뀔 때마다 저장하는 방식을 택했습니다.
Q9. UTF-8은 왜 지정했나요?
인코딩은 글자를 저장할 숫자로 바꾸는 약속인데, 읽을 때와 쓸 때 약속이 다르면 한글이 깨집니다. 문제가 전부 한글이라 읽기·쓰기 모두 encoding="utf-8"로 통일했습니다. 추가로 ensure_ascii=False 옵션을 줘서 파일을 열었을 때 한글이 코드가 아니라 글자 그대로 보이게 했습니다.
Q10. (직접 abc를 입력해보며) 이건 어떻게 처리했나요?
숫자가 필요한 모든 곳에서 input_int()라는 함수 하나를 씁니다. 이 함수가 네 가지를 순서대로 검사합니다. ① 앞뒤 공백 제거 ② 빈 입력인지 ③ 숫자로 바꿀 수 있는지 ④ 허용 범위 안인지. 하나라도 실패하면 안내 메시지를 출력하고 다시 입력받는 자리로 돌아갑니다. 프로그램은 절대 종료되지 않습니다.
Q11. 저장 파일이 깨지면 어떻게 되나요?
try/except로 감싸놨습니다. 파일이 깨졌거나, 형식이 이상하거나, 필요한 항목이 없는 경우를 전부 잡아서 “⚠️ 저장 파일이 손상되어 기본 퀴즈로 복구합니다”를 출력하고 기본 퀴즈 5개로 정상 실행합니다. 파일이 아예 없는 경우도 마찬가지로 기본 퀴즈로 시작합니다. 직접 파일을 지우거나 망가뜨려서 확인해보셔도 됩니다.
Q12. Git이 뭐고 왜 쓰나요?
코드의 변경 이력을 기록하고 원하는 시점으로 되돌릴 수 있게 해주는 도구입니다. 게임의 세이브 파일과 같습니다. Git이 없으면 “최종”, “진짜최종”, “진짜최종_수정” 같은 파일이 쌓여서 뭐가 최신인지 알 수 없게 됩니다. 저는 기능 하나를 완성할 때마다 커밋해서 총 17개의 기록을 남겼습니다.
Q13. add와 commit은 뭐가 다른가요?
add는 이번에 기록할 파일을 장바구니에 담는 것이고, commit은 계산해서 영수증을 받는 것입니다. add 단계가 따로 있는 이유는, 파일을 여러 개 고쳤더라도 관련 있는 것만 골라 담아서 커밋을 의미 있는 단위로 나눌 수 있게 하기 위해서입니다.
Q14. commit과 push의 차이는요?
commit은 내 컴퓨터 안에만 저장되고, push는 그 기록을 GitHub(인터넷)에 올립니다. 커밋만 하고 push를 안 하면 GitHub에는 아무것도 없습니다. 제출이 GitHub 주소로 이뤄지니 push가 꼭 필요합니다.
Q15. clone과 pull은 어떻게 다른가요?
clone은 저장소를 이력까지 통째로 처음 한 번 내려받는 것이고, pull은 이미 받아둔 것을 최신 상태로 갱신하는 것입니다. 앱을 처음 설치하는 게 clone, 이미 깔린 앱을 업데이트하는 게 pull이라고 보면 됩니다.
Q16. 브랜치는 왜 썼나요? 혼자 하는데 필요한가요?
혼자 해도 필요합니다. 브랜치는 원본을 건드리지 않고 따로 실험하는 공간이라, 새 기능을 만들다 망가뜨려도 main은 항상 정상 상태로 남습니다. 저는 이 프로그램에서 가장 복잡한 “퀴즈 풀기” 기능을 feature/play-quiz 브랜치에서 만들고, 랜덤·문제 수 선택·힌트까지 붙여서 정상 동작을 확인한 뒤 main에 병합했습니다.
Q17. 커밋 메시지를 왜 그렇게 썼나요?
나중에 이력만 봐도 무슨 작업을 했는지 알 수 있게 하려고 규칙을 정했습니다. 새 기능은 Feat:, 오류 수정은 Fix:, 문서는 Docs:, 코드 정리는 Refactor:를 앞에 붙였습니다. “수정”처럼만 쓰면 일주일 뒤에 제가 봐도 뭘 고쳤는지 모르기 때문입니다.
Q18. .gitignore에 state.json을 넣은 이유는요?
state.json은 코드가 아니라 실행하면 자동으로 만들어지는 개인 플레이 기록입니다. 사람마다 다른 데이터라 저장소에 올릴 이유가 없고, 파일이 없어도 프로그램이 기본 퀴즈로 알아서 시작하도록 만들었기 때문에 제외해도 아무 문제가 없습니다. 저장소에는 코드와 문서만 남습니다.
Q19. 외부 라이브러리를 안 쓴 게 맞나요?
네. json, os, random, datetime 네 가지만 썼는데 전부 파이썬에 기본 포함된 표준 라이브러리입니다. 따로 pip install로 설치한 것은 없어서, 파이썬 3.10 이상만 있으면 어느 컴퓨터에서든 바로 실행됩니다.
Q20. 만들면서 가장 어려웠던 점은 뭐였나요?
저장과 불러오기였습니다. 파이썬 객체는 파일에 그대로 쓸 수 없어서, 객체 → 딕셔너리 → JSON 글자로 바꿔서 저장하고, 불러올 때는 정확히 반대 순서로 되돌려야 했습니다. 이걸 to_dict()와 from_dict()라는 짝을 이루는 메서드로 만들어 해결했고, 이 과정에서 “객체는 메모리에만 있고, 파일에 남기려면 변환이 필요하다”는 걸 이해하게 됐습니다.
